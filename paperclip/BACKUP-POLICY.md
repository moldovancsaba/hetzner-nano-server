# Daily recovery backups

Paperclip creates one full recovery point each day at 03:20 Europe/Budapest. Retention is seven days on both the server and owner Mac. The separate hourly native database backup is disabled; the Mac LaunchAgent has only its daily calendar trigger, with its existing guarded startup check.

Each full archive contains one newly completed native SQL snapshot, the consistent factory SQLite snapshot and the existing persistent files, deployment configuration and credentials. Rolling SQL history and live PostgreSQL files are excluded. This avoids copying the entire hourly history into every daily archive. The archive also includes the deployed GDS dashboard, its private proxy import and factory service overrides. Verification requires every script and stylesheet referenced by the modern dashboard shell, and any imported dashboard proxy configuration. An incomplete modern archive cannot be acknowledged or authorize retention. The existing private archive format remains compatible with legacy factory snapshots.

The Mac verifies the archive checksum, required components, gzip integrity and factory SQLite integrity before acknowledging it to the server. Only then can retention remove older recovery points and reduce legacy hourly SQL history to daily points. Expiry uses capture time, not the number of manual runs. A newer verified point replaces an earlier point from the same Budapest calendar day. The most recent verified point is always protected, including when a future backup fails. Missing verification or a changed latest checksum holds cleanup. Unknown filenames and symbolic links are not cleanup targets.

The native SQL directory is also reduced to daily points within seven days after a verified off-server acknowledgment. This does not touch the live database or its WAL. Daily backup frequency and retention are independent of business jobs, search budgets and notification schedules.

## Recovery and operations

Run backup.py through its existing daily LaunchAgent. Both SSH control calls and archive transfers explicitly use the saved macOS Keychain identity with batch mode, a connection deadline and only the configured key. An unlocked SSH agent is not required when the key is already available in Keychain. Never request or log the passphrase. A manual `--force` run is an explicit recovery verification and replaces an earlier same-day point only after verification. `--prune-only` applies the same local retention without creating a snapshot; scheduled-backup.py `prune` applies the server archive policy. Both require a current verified point. No hourly wake or new timer is installed.

archive_snapshot.py refuses absent, corrupt or incomplete fresh SQL, existing output paths and non-private output directories. An incomplete output remains private for inspection and is never marked verified. backup_retention.py implements the shared age and daily-point policy on both hosts. Existing verified snapshots stay available if transport, checksum, gzip, SQLite or acknowledgment fails.

The 6 November recovery temporarily reduced the root filesystem's reserved block count from 401138 to 100000 after disk exhaustion. The original count is restored after verified retention recovered sufficient headroom. That reservation is emergency space, not additional storage capacity. Application startup recovery and the original data volumes remain authoritative; no old database is restored over current writes.

The isolated restore uses a half CPU, an 1800 MiB container limit and a 1280 MiB application heap, with host-memory admission before startup. The SQL restore deadline scales with dump size and remains capped at fifteen minutes. The complete historical metrics response has a separate bounded rehearsal allowance matching the isolated reader deadline; measured latency is reported and does not establish a production performance target. Other HTTP checks retain their existing limits. Agents, routines and automatic backups are disabled in the clone; its network has no external route. The clone serves the captured GDS shell through its own factory route and checks every referenced script and stylesheet through the restored browser gate. Authentication is minted per request so startup waiting cannot expire the later verification session. Production memory settings remain unchanged.

Current rollout, cleanup and isolated restoration evidence is in [maintenance verification](maintenance-verification-20261106.json). Earlier failed rehearsal diagnostics remain private; replacement-host DNS/TLS and real failover require separate verification.

The heartbeat recovery lookup requires the run-text and fallback-issue indexes in `ops/heartbeat-run-text-index.sql`; native SQL captures retain them automatically. Its bounded installation does not change business records. Older recovery points need the same idempotent repair before metrics verification. Check the actual query plan and authenticated metrics response before declaring recovery. PostgreSQL may defer a new index while older transactions remain visible; preserve those transactions and wait for normal completion. See the [PostgreSQL index catalog](https://www.postgresql.org/docs/current/catalog-pg-index.html) for the visibility rule.

Company reporting uses the peer-authenticated local reporting socket for the restricted factory account. Only its configured company and pinned native read model are allowed; database sessions are read-only and no operational recovery workflow is called. The factory receives the narrow reporting group, never Docker access. The installed socket units and service override are included in recovery captures; provision the dedicated reporting group on a replacement host before enabling them. This is request activation, with no timer. The isolated rehearsal uses its own container directly under its root maintenance process. Its native read allows three minutes and its metrics request allows additional transport and assembly time within a fixed outer verification deadline. These limits account for cold history reads under the existing half-CPU resource ceiling; production reader and browser deadlines are unchanged. Its container selector and local-trusted mode must be restored together with the reader.
